# 降级约定：局部异常只伤局部

这份文档不是「理想」，是对已经付过学费的地方立的规矩。PilotV 是常驻多会话服务，
一次外部依赖抖动就整进程退出，代价是**所有**在线会话掉线。所以下面每一条都能对应到
一次真实故障或一次真实修复，没有一条是预防性想象。

配套阅读：`docs/HANDOFF-Windows-20261105.md`（三处上游缺陷的完整取证）。

---

## 1. 总原则

**部分结果 > 全失败，但降级必须可见、可归因、有边界。**

三句话缺一不可。只说「部分结果 > 全失败」，得到的是静默出错：用户看到一片空白，
以为模型是空的；看到设备列表少一台，以为是自己记错了。**看不出来的降级比失败更坏**，
因为失败会逼人来看，降级不会。

因此每个降级点必须同时回答三个问题：

1. **用户看到的和「正常但慢」能区分吗？** 不能区分就是静默降级，不合格。
2. **留下可查的痕迹了吗？** 要有日志（带 correlation id）+ 可被 `/healthz` 或接口读到的状态。
3. **失败的边界等于这次操作的作用域吗？** 一个会话的压缩失败不该让别的会话变慢，
   一台设备的成果台宕机不该让整个网关 502。

**不可降级的东西**（降级 = 制造安全漏洞或伪造成功）：

| 不许降级 | 为什么 |
|---|---|
| 代理目标白名单 / 内网判定 | 未知地址一律不转发。报错也不能把用户给的地址原样回显成可执行内容 |
| 管理写操作的会话校验 | 设备写接口能往白名单加地址，等于决定流量送往哪台内网机器 |
| 原子写（临时文件 + rename） | 前端随时在读 `devices.json`，半个 JSON 会让切换器整个消失，看起来像前端 bug |
| 坏配置的外扩 | 源清单有问题时绝不写进 `dist/`；宁可留着上一份好清单 |
| 「读不到」冒充「空」 | 文件不存在 ≠ 清单为空；给空清单会让所有下游以为「一切正常」 |
| 端口被别人占用时抢着重启 | 那不是我们的进程，`watch` 等它就对，杀掉才是事故 |

## 2. 已经在这么做的地方（作为范例）

**摘要截断接受部分结果** — `pilotdeck-mobile/upstream-official/src/context/compaction/CompactionEngine.ts:426`
摘要顶到输出上限（`COMPACT_MAX_OUTPUT_TOKENS = 4000`）是**可预期常态**，原版却 `throw`。
后果链：被 `run()` 捕获 → 设 `summarySucceeded: false` → 压缩不落地 → 会话继续膨胀 →
下一轮再触发 → 再失败，没有任何出口，最后诱发整进程退出。
现在：`console.warn` + 用已生成的部分摘要让压缩落地（`:431`）。
**这条是全仓库降级原则的原型**，其余各处照它对齐。

**次要 promise 失败不杀进程** — `src/cli/runtimeCrashGuards.ts:34`
`unhandledRejection` 只记完整原因 + 上报，**不退出**；`uncaughtException` 仍退出
（同步的状态损坏不可幸存），但先把完整堆栈打进日志。

**解码降级为替换字符** — `src/tool/builtin/bash/commandRunner.ts`
Windows 上子进程输出混 GBK/UTF-8 是常态。`TextDecoder("utf-8")` 不带 `fatal`，
非法字节降级成 U+FFFD：命令输出里少一个字符，比整进程 `uncaughtException` 好一万倍。

**返工单三通道各自独立汇报** — `artifacts_deliver.py:18`
意见要落三处：原项目目录（`write_rework_order`）、会话输入队列（`enqueue_session_input`）、
既有 dispatch 唤醒。三个通道**成败各自返回 `{ok, reason}`**，不做「看起来成功了」的合并。
典型场景：会话正在实时跑时不写 `pending-inputs`（那份文件正被 gateway 持有内存态随时整体
覆写，写进去会被无声抹掉）—— 这时如实说「没排进对话，但已落盘」，而不是回一个 200。

**能力缺失如实 503** — `artifacts_cad.py:42` / `artifacts_console.py:2408`
转换器没装就抛 `CadUnavailable`，接口回 503 并带上一次性安装命令。
反面做法是返回空白 GLB：用户以为模型是空的，会去重做已经做对的建模。

**取不到元数据时取保守值** — `artifacts_deliver.py:691`
`pdfinfo` 拿不到页数就按 1 页处理，至少第一页还能看。注意它是「**少给**」而不是「假给全部」。

**故障只降级出问题的那条会话** — `src/gateway/health/SessionHealthTracker.ts`
连续 2 次失败才判 degraded（一次抖动不算病），`turn_completed` 或压缩成功即恢复。
`observe()` 内部吞掉自己的一切异常 —— 它坐在事件流的必经之路上，
**监控自己坏了不能顺手把业务也带下去**，这是降级原则用在可观测性自己身上。

**探活永不 5xx** — `src/gateway/server/GatewayServer.ts:91` 的 `/healthz`
局部降级时 `/healthz` 仍返回 200 + 降级明细。若它跟着 5xx，supervisor 会把
「一台设备连不上」判成「进程死了」而重启一个本来健康的网关，把降级放大成事故。
（既有 `/health` 的语义不动，别处在用。）

**重启决策宁可不作为** — `service/supervisorPolicy.mjs:131`
只有网关自报 `ok:false` 或 healthz 过期才 restart；端口被别人占一律 `watch`。

**坏清单只报不拦** — `service/pilotv_gateway.mjs:781`
带坏条目启动（能用的那几条仍可用）比拒绝启动更可用，但问题必须显眼。
同一条逻辑的边界：`dist-missing` 时不越权创建目录 —— dist 是构建产物，
网关没资格替 vite 决定「现在该有一个 dist 了」。

**未知设备显式报错** — `service/deviceManifest.mjs:164`
按来源分开处理：`?d=` 是显式意图，当场 409 列出可用设备；
Cookie/头里的陌生地址多半是改名残留，带着 `stale-selection:<origin>` 回落本机
（否则人会被自己的 Cookie 锁死在「哪里也去不了」上）。

**产物基线不占回合** — `src/session/artifacts/FileArtifactCollector.ts`
每轮开头要给整个工作区拍基线快照（算 sha256），真实项目几百 MB，冷缓存时能吃
几十秒；两个会话在同一项目里并发还会同时扫同一棵树。现在基线在后台抓、扫描有
预算（默认 8s）、同工作区共享一次结果。**降级方向是「少报」**：基线没扫完、
或基线期间就已经有写操作，本轮放弃整树 diff，只收工具显式报出来的文件 ——
宁可少报一个产物，也不把别人改的文件算到这一轮头上。

**会话级 MCP 池满时回收而不是丢工具** — `src/cli/createLocalGateway.ts:956`
每个 per-session MCP 条目是一个子进程（browser-use 会拉起浏览器），池按
`gateway.maxPerSessionMcpInstances` 封顶。旧代码池满就直接跳过，新会话**静默**
失去 `browser_*` 工具，界面上看不出来。现在按 LRU 回收一个没有在跑回合的槽位，
并把那个会话标脏（下一轮重建运行时，不拿着已经停掉的工具）；只有全部槽位都在
跑的时候才拒绝，且日志要列出是谁占着、怎么调大配额。

## 3. 新代码怎么判断该不该降级

按顺序问：

1. **这是正确性/安全边界吗？** 是 → 不许降级，如实失败。第 1 节表格里的东西都在这一层。
2. **降级后交付的东西变少但仍然是真的吗？** 是 → 降级，并明确说少了什么。
   （部分摘要是真摘要；空白 GLB 不是「少一点」的模型，那是假东西。）
3. **失败的爆炸半径能限制在这次操作内吗？** 能 → 只标记这次操作/这个会话/这台设备失败。
   不能 → 那要修的是隔离，不是加降级。
4. **降级原因能被用户和排障者分别看到吗？** 用户侧一句人话 + 日志侧带 id 的完整堆栈。
   两边缺一边都算没做完。
5. **这是可预期常态还是真意外？** 常态（截断、编码混杂、可选依赖缺失）→ 降级路径要
   有测试。真意外 → 让它响，别用 `catch` 包住，包住的代价是下一轮排查多花两轮。

## 4. 禁止事项（都是从误判里总结的）

- **不要用 telemetry 代替日志。** `trackError` 会把错误压成一个 code，堆栈就地消失
  （`src/telemetry/collector.ts:85` → `normalizeErrorCode`）。缺陷 B 那轮排障前两次
  误判为「无异常优雅退出」，直接原因就是日志里只剩 `[telemetry] shutdown snapshot`。
  **上报和打日志是两件事，做了前者不等于做了后者。** 由 `scripts/ci/check-error-observability.mjs` 拦。
- **不要静默回落。** 「切不过去但没原因」和「网络慢」在用户眼里长得一样，
  于是所有排查精力都花在错误的方向上。
- **不要把「读不到」返回成空集合。** 调用方无法区分，只能往下猜。
- **不要为了「不报错」而改写响应。** 例如把远端成果台的诚实 404 改写成内容类型错误的
  假 200（`service/pilotv_gateway.mjs:253` 注释里记着这个尝试为什么被放弃）。
- **不要在事件流主路径上让监控代码具备杀伤力。** 见 `observe()` 的自吞异常。
- **不要用「重启」掩盖慢性病。** 退避 + 计数 + 告警；重启能修好一次抖动，修不好设计缺陷。

## 5. 还没做到的（按优先级）

| 位置 | 现状 | 应该 |
|---|---|---|
| 摘要/翻译之外的 LLM 二次调用 | 各写各的 try/catch | 统一走「部分结果 + 原因 + 不重试风暴」的形状 |
| 成果交付的部件树 | 缺 `parts.json` 时退化为单个隐式根部件（对）；部件文件本身丢了会怎样未测 | 逐个部件报缺失，其余照常渲染 |
| 附件转码并发满 | 直接排队等待，界面无提示 | 降级为「先给原文件 + 后台转」 |
| 上游 vendor 更新 | 三处修复可能被覆盖回原版 | patch 系列 + CI `git apply --check`（P3.4） |

发现新的可降级点或新的静默降级，补进第 2/4 节，并让 `pilotv doctor` 能查出来 ——
**检查早就有、缺的是执行者**，这条教训在本仓库已经重复出现过四次。
